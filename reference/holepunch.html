Before you start

Ground rules

  • No git init, commits or GitHub until you say so. Phase 16 is gated.
  • Required work first. Stretch only after the clean-room Docker test passes.
  • The spec suggests 2–4 hours. A finished core beats a half-built stretch goal.
  • Fictional patient data only. Nothing real goes in seeds, logs or screenshots.

Easy points to lose

  1. GET /health must return exactly {"status": "ok"}.
  2. Seeding runs automatically on startup, not through a manual script.
  3. POST …/notes accepts a timestamp from the client. Don’t only auto-generate it.
  4. Search, filter and sort must work across every page of results, so they run on the server.
  5. Deep links like /patients/12 must survive a browser refresh in the Docker build (nginx SPA fallback).
  6. Validation runs on both client and server, and server errors reach the user.
  7. docker compose up works on a clean machine with no extra steps.
  8. The layout has to hold up at lower resolutions. Test narrow widths.

How we’re reading the ambiguous parts
“15–20 patients minimum” vs. “handle 100+ efficiently”
Seed the 100 invented patients from prior-auth-pack. That clears the minimum and gives real volume for the 100+ check.
“Pagination or infinite scroll”
Page-based pagination. Simpler, and it keeps the list state in the URL.
“Dockerfile for the frontend (or serve via the backend)”
A separate nginx container, which matches the three services compose has to start.
“An LLM can be helpful, but a template is acceptable”
Template by default so it runs with no keys. An LLM is optional, behind the same interface.
“PUT /patients/{id}”
Full replacement. No PATCH, since it isn’t asked for.
“Contact” and “address”
Contact = phone + email. Address = line 1, line 2, city, state and postal code as columns.
“Age”
Computed from date of birth when read, never stored.
“Choose 1–2 stretch features”
Claim two: Alembic migrations and API unit tests. Overlaps such as server-side sort/filter get a one-line mention.
